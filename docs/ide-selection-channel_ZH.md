# IDE 选区通道

键入 `@路径#L12-14` 引用当然可用，但它要用户记一套按键，而且它从磁盘读文件——只要缓冲区有未保存的修改，读到的就是错的。IDE 选区通道一次解决这两个问题：编辑器推送**实际选中**的内容，dsh-TUI 在提交时再附加。

## 形态

扩展激活时在 `127.0.0.1` 的随机端口上起一个**回环 WebSocket 服务端**，并用两种方式公布它：

- **环境变量直连。** 扩展启动的终端会拿到 `DSH_TUI_IDE_PORT` 与 `DSH_TUI_IDE_TOKEN`，无需查找即可连接。
- **lock 文件兜底。** `~/.dsh-tui/ide/<port>.lock` 内容为 `{port, token, workspaceFolders, pid}`，让用户手动启动的 dsh-tui 能扫描该目录并按工作区匹配到服务端。目录权限 `0700`，文件 `0600`；在 Windows 上这些 mode 位只能落到「只读」属性上，因此 token 区分的是**进程**，而不是本机账户。

只使用回环地址，token 每个服务端实例一份。

## 握手

协议版本为 2：客户端发送 `ide/hello`，携带 token 与自身协议版本；服务端回 `ide/hello_ack`，带上自己的版本与工作区文件夹列表。token 或版本不符即拒。

工作区文件夹列表只能缩小候选范围。当多个 VS Code 窗口打开**同一个**工作区时，每一份锁文件都匹配，手动启动的 dsh-tui 会按端口号顺序取第一个——所以它可能连到另一个窗口。

## 启动期连接

扩展启动的会话知道该去哪：端口与 token 来自环境变量，本窗口的服务端会被优先拨号。扩展会等服务端开始监听后再创建终端（启动失败时照常创建），所以刚打开窗口就点击，拿到的终端其环境变量依然指名本窗口的服务端，而不是只能靠扫描去猜。

手动启动的会话则必须扫描，而它的首次拨号可能输给一次卡顿：加载 DSH 内核会让主线程连续阻塞数百毫秒到数秒，而单次尝试的预算是 300ms。包含上游连接期重试的 dsh-tui 版本会继续尝试——再按 0.5s / 1.5s / 3s / 6s 的退避间隔尝试四次，每次仍受 300ms 限制，整个窗口因此最坏约为 12.5 秒（首次尝试 + 4 次重试，每次 ≤300ms，再加 11 秒退避）。每次尝试都会重新扫描 `~/.dsh-tui/ide/`，所以 TUI 启动之后才写下的锁文件仍会被看到；一旦握手成功，待定的尝试就全部取消。

重试只到首次连接成功为止。连接掉线之后，通道仍按原设计静默降级：缓存选区被清空、徽标消失，直到下一次会话或工作目录改变之前都不会重连。

已知边界：

- **一个工作区开着多个窗口。** 两份锁文件都匹配，客户端按端口号顺序取第一个，所以手动启动的 TUI 可能落到另一个窗口的服务端上。扩展启动的会话优先直连自己的窗口（环境变量直接指名本窗口的服务端）；该候选失败时仍会回退到 lock 扫描，极端情况下仍可能命中同工作区的另一个窗口。
- **卡顿长于重试窗口。** 约 12.5 秒是一份固定的上限；足够慢的机器仍可能整个会话都没有通道，重试不是无上限的。
- **已经过期的选区。** 服务端只能补推它最后听到的那一帧（见下文），所以一个没有推送空选区就关闭的编辑器，会把这份记忆留在那里。

## 推送什么

选区变化防抖 **300ms** 后以 `selection_changed` 通知发出：

```json
{ "path": "…", "startLine": 0, "endLine": 2, "isEmpty": false, "text": "…", "documentVersion": 7 }
```

行号为 0-based，`text` 是编辑器缓冲区自己的选区文本——含未保存修改——`documentVersion` 供接收侧判断新鲜度。dsh-TUI 原样附加该块，而不是去重读一个可能已经过期的文件，并显示 `⧉ Selected N lines from …` 指示行。

推送上限为 20 万字符，高于 dsh-TUI 自己的 5 万字符上限，所以这道上限是带宽与内存护栏，而不是正确性边界。

把 `dsh-tui-vscode.autoInsertMention` 关掉并不只是停止推送：它会先取消待发的防抖推送，再发一次空选区通知，这样 dsh-TUI 手里已经持有的快照就不会被附加到下一条消息上。

晚连上的客户端不必等下一次选区变化：服务端记住最近一次非空选区，并在 `hello_ack` 之后立即补推一次；空选区会清掉这份记忆。若该帧已经以 `@路径#L…` mention 键入过终端（即下方的回退），扩展会登记这一帧的指纹并跳过补推，一条消息因此不会带两份同样的上下文。指纹只存在内存里，扩展宿主重启后即丢失。

## 通道不可用时

扩展回退为把 `@相对路径#L起-止` 键入运行中会话的终端。这个回退有自己的前提：必须存在一个由本扩展持有的会话终端。终端是按名字匹配的，所以即使其中的 dsh-tui 已经退出，它依然算数——引用会被键入终端而不是进剪贴板，停在提示符上的 shell 会原样收到这行文本。既没有客户端也没有终端时，什么都不会键入。

## 生命周期

服务端启动失败会静默降级——扩展其余部分照常工作，失败只记入日志。停用时清理 lock 文件与监听器，且**先做一次同步停止**：`start()` 是异步的，若扩展在它 settle 之前就停用，一次只清理「已创建的句柄」的停止会留下无人持有的服务端。宿主可能不等微任务队列排空就退出，所以那次同步清理很重要。

## 版本门槛

握手的双方都随 **dsh-tui 0.11.0** 到来；dsh-tui 0.10.x 里根本没有 `ide-channel` 模块。到 0.15.0，`IDE_PROTOCOL_VERSION` 仍是 `2`；扩展侧的那一半——会说协议 v2——随 **dsh-tui-vscode 0.7.0** 到来。

连接期重试晚于上述两道门槛，需要包含上游修复的 dsh-tui 版本；**目前还没有已发布的 dsh-tui 包含它**。没有该版本时，首次拨号失败仍会让这个会话失去选区通道。

更早的设计记录 [at-mention-design_ZH.md](at-mention-design_ZH.md) 是 **0.6.2–0.6.3 快照**，描述的是通道出现之前的行为（包含「引用用绝对路径」那一版），请当作历史看待。
