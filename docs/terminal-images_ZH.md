# 终端图片——这道门禁为什么长这样

README 只写了三个前置条件与两个设置项。本文记录扩展为什么这样判断、刻意不声称什么，以及哪个问题仍然悬着。

## 这套机制要防的失效

条件不满足时，图像区域必须显示**半块字符画**，绝不能是一片空白。

扩展为它启动的每个会话导出 `DSH_TUI_IMAGE_PROTOCOL`。`sixel` 向 dsh-tui 要真实栅格图；`none` 要字符画兜底；`auto` 则把该变量整个移除，交回 dsh-tui 自行判定。

`auto` 是「移除」而不是「不写」，因为 VS Code 会把传给 `createTerminal` 的环境**叠加**在终端原本要继承的环境之上。只把键留着不写，会让你的 shell profile 导出的值、或从 VS Code 进程继承来的值抵达 dsh-tui，把它悄悄钉在某个协议上——而那正是 `auto` 想逃离的状态。

钉协议这件事的起因是：VS Code 的 `@xterm/addon-image` 对 Kitty 图形查询回了一个 `OK`，却从未真的画出来，而 dsh-tui 优先选 Kitty 而非 Sixel。于是立绘被擦掉后再也没重绘。钉住 Sixel 就绕开了这条路径。

## 三个观测

VS Code 没有「当前实际使用哪个渲染器」的 API，扩展没法直接问「这个窗口能不能画图」。它改为读三个值：

1. **`terminal.integrated.enableImages`，在 `activate()` 时快照一次**，本窗口内刻意不刷新。
2. **`terminal.integrated.gpuAcceleration`**，同一时刻快照。
3. **实时的 `terminal.integrated.enableImages`。**

只有三者都放行，会话才会拿到 `sixel`。窗口启动快照的存在，是因为扩展无法观测 VS Code 究竟何时建立终端的渲染器；实时读则用来抓住「窗口运行期间把设置关掉」这种情况。

实际后果是：打开 `enableImages` 对**同一个窗口内**启动的会话不生效。扩展会继续导出 `none`，图像区域以字符画保持可见，并且每次会话启动都会说明这一点并提供**重载窗口**按钮。只有重载之后启动的会话才会拿到 `sixel`。

这条重载提示**刻意不是一次性的**。只要状态没变，它每次会话启动都会再次出现。被「只问一次」的是**启用引导**，且带一个刻意的例外：如果那次设置写入失败了，就是什么都没写进去，于是下次会话启动会再给一次一键路径，而不是把你卡住。这次重试由**本窗口自己的状态**保证，而不是靠持久标记——清除标记是「发出去就不管」的异步写，被延迟或被拒绝都不能把刚做出的承诺压掉。

## 设置作用域

`terminal.integrated.enableImages` 是窗口作用域，所以工作区级或文件夹级的覆盖会压过扩展写入的全局值。「写进去了却不生效」本来会被当成成功。

因此扩展会在写入**之前**用 `Configuration.inspect()` 看每个作用域显式设了什么，并由**最高优先级的那个「已定义」作用域**说了算——文件夹级 > 工作区级 > 全局，而「什么都没设」的作用域只意味着跳过它，既不当作覆盖，也不当作成功：

- 该决定性作用域里显式的 `false` 会压过这次全局写入。此时一个字都不写，给你的是手动指引而不是重载引导。
- 那里的 `true` 说明设置本来就已生效，于是照常写入，重载引导照常给出。

判定刻意**不在写入之后回读**该设置。`Configuration.update()` 会在新值抵达扩展宿主之前就 resolve，那时读到旧值会把一次成功的点击误报成失败。

## 残余风险

以下是已知且不声称已解决的：

- VS Code 没有报告「当前渲染器是哪个」的 API，这道门禁做不到精确。
- 在没有可用 GPU 的机器上，`gpuAcceleration: auto` 仍可能落到 VS Code 的 **DOM 渲染器**（其非 WebGL 渲染器）。门禁在那里会放行 `sixel`；真正让最差情况免于空白的，是字符画兜底。
- 窗口运行期间改动 `gpuAcceleration`，要等重载（重启扩展宿主）后才会被重新读取。

## 版本门槛

`DSH_TUI_IMAGE_PROTOCOL` 在 dsh-tui 0.9.0 与 0.9.1 中不存在，自 **0.10.0** 起存在；到 0.15.0 仍在读取（`lib/types/ink/ink.js`），且 dsh-tui 仍优先 Kitty 而非 Sixel，所以钉住 Sixel 依旧成立。扩展侧的那一半——「是否注入这个变量」——随 **dsh-tui-vscode 0.7.5** 到来。

运行时实测组合：Windows 11 (10.0.26200) + VS Code 1.140.0 + dsh-tui 0.15.0——本扩展的真实扩展宿主 e2e 套件在此通过，其中包含「恢复一个真实 dsh-tui 会话」的受保护用例。其他平台、远程环境与其他 VS Code 版本均未验证。

## 未决问题

扩展的门禁建立在「必须重载」这个假设上。阅读 VS Code 1.140.0 的产物则提示一条更宽的规则：addon 是**按终端**评估的——在某个终端的 WebGL 渲染器被建立时评估。已存在的终端保留旧状态，但设置改变之后**新建**的终端会读到实时值并真的挂上 addon，而本扩展每个会话都会新建终端。

若这个读法成立，那么门禁给出的**理由**过强了，而门禁本身与「请重载」的建议依然成立（真正抑制 `sixel` 的是扩展自己的窗口启动快照）。要定论不需要改代码：不重载窗口就把 `terminal.integrated.enableImages` 打开，启动一个会话，然后向那个终端发一次主设备属性查询（DA1）。回复里若声明了 Sixel，说明 addon 已经挂到了这个窗口里新建的终端上；原生渲染器不会声明它。
